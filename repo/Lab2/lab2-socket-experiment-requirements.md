# 实验二：基于 Socket 接口实现自定义协议通信

依据：`lab2/report2-socket.docx`

## 一、实验目标

- 使用 Socket 编程接口编写基本的网络应用软件。
- 掌握 C 语言形式的 Socket API，正确发送和接收网络数据包。
- 编写一个具有交互菜单的客户端。
- 编写一个能够并发处理多个客户端的服务端。
- 使用自定义协议完成客户端与服务端之间的通信。

程序界面不作特殊要求，可以使用命令行或最简单的窗体。

## 二、硬性要求

1. 运输层协议必须使用 TCP。
2. 网络数据包收发部分只能使用底层 C 形式的 Socket API，不能使用 Socket 封装类。
3. 客户端和服务端都必须采用多线程模式。
4. 服务端监听端口必须使用学号后四位。
5. 客户端和服务端必须能够同时处理多个连接。
6. 需要处理 TCP 的分片、合并和部分发送问题，不能假定一次 `send()` 或 `recv()` 就对应一个完整报文。
7. 客户端未连接时，只能选择“连接”和“退出”。
8. 客户端发送消息前必须先获取客户端列表。
9. 服务端必须将收到的消息转发到指定编号的客户端。

### Windows API 对应关系

- 初始化：`WSAStartup()`
- 创建套接字：`socket()`
- 客户端连接：`connect()`
- 服务端绑定和监听：`bind()`、`listen()`
- 接收连接：`accept()`
- 发送和接收：`send()`、`recv()`
- 关闭套接字：`shutdown()`、`closesocket()`
- 结束 Winsock：`WSACleanup()`
- 获取计算机名：`GetComputerNameA()` 或 `GetComputerNameW()`
- 编译时链接：`Ws2_32.lib`

报告中的 `receive()` 应按实际平台使用 `recv()` 实现；不得使用 `QTcpSocket`、Boost.Asio 等 Socket 封装类。

## 三、客户端功能

客户端采用交互菜单，必须包含以下 7 项：

1. **连接**：输入服务器 IP 和端口，调用 `connect()`，显示连接结果；连接成功后创建接收数据子线程。
2. **断开连接**：关闭当前连接，设置为未连接状态，通知并等待接收子线程退出。
3. **获取时间**：请求服务端发送当前时间，并显示响应。
4. **获取名字**：请求服务端发送其机器名称，并显示响应。
5. **活动连接列表**：请求服务端发送当前客户端的编号、IP、端口等信息，并显示列表。
6. **发消息**：输入目标客户端编号和消息内容，请求服务端转发；接收客户端必须显示发送者编号、IP、端口和消息内容。
7. **退出**：已连接时先断开，再退出；未连接时直接退出。

### 客户端线程职责

主线程负责：

- 显示菜单和读取用户输入。
- 发送请求。
- 处理接收子线程放入的消息队列。
- 显示时间、机器名、客户端列表和转发消息。

接收子线程负责：

- 循环调用 `recv()`。
- 拼接并解析完整数据包。
- 将响应消息或指示消息放入线程安全消息队列。
- 收到主线程退出通知后结束。

主线程不能因为等待用户输入而完全停止处理接收消息；转发消息到达时应及时显示。

## 四、服务端功能

服务端启动流程：


```text
WSAStartup -> socket -> bind(学号后四位端口) -> listen -> 循环 accept
```

服务端主线程必须：

- 创建监听 Socket。
- 绑定学号后四位端口。
- 调用 `listen()` 设置连接等待队列。
- 循环调用 `accept()`。
- 为每个新客户端建立编号、Socket、IP、端口和连接状态记录。
- 创建客户端处理子线程后继续调用 `accept()`。

每个客户端处理子线程必须使用本次 `accept()` 返回的已连接 Socket，不能使用监听 Socket 进行业务收发。

### 服务端请求处理

| 请求类型 | 服务端动作 |
|---|---|
| 获取时间 | 调用 `time()` 获取本地时间，通过 `send()` 返回客户端 |
| 获取名字 | 调用 `GetComputerNameA/W()` 获取机器名，通过 `send()` 返回 |
| 获取客户端列表 | 读取客户端表，返回编号、IP、端口等信息 |
| 发送消息 | 按目标编号查找客户端，用目标客户端 Socket 转发消息 |

客户端断开或通信出错后，服务端必须清理其客户端记录和 Socket。

## 五、协议实现要求

实验报告没有规定具体报文格式，报文格式需要自行设计；客户端和服务端必须使用同一格式。

推荐使用固定长度报头加变长正文：

```text
报头：type(4 字节) + request_id(4 字节) + body_len(4 字节)
正文：body_len 字节
```

建议约定：

- 所有整数使用网络字节序，通过 `htonl()`、`ntohl()` 等函数转换。
- 不直接发送包含指针或 `std::string` 的 C++ 对象内存。
- 为正文设置最大长度并校验 `body_len`。
- 请求、响应、转发指示消息使用不同类型编号。
- `request_id` 用于匹配请求和响应；服务端主动转发消息可以使用特殊值。

必须编写类似以下功能的底层辅助函数：

- `send_all()`：循环调用 `send()`，直到完整发送指定字节数。
- `recv_exact()`：循环调用 `recv()`，直到接收指定字节数或发现断开。
- `send_packet()`：编码报头和正文后完整发送。
- `recv_packet()`：先读取报头，再按正文长度读取完整报文。

这些是收发辅助函数，不应被实现为高层 Socket 封装类。

## 六、建议的代码目录

客户端和服务端源代码必须分别放在不同目录。可以采用以下结构：

```text
lab2/
├─ client/
│  ├─ client.cpp
│  ├─ receiver.cpp
│  └─ protocol.h/.cpp
├─ server/
│  ├─ server.cpp
│  ├─ worker.cpp
│  └─ protocol.h/.cpp
├─ client.exe
└─ server.exe
```

也可以分别使用一个 `.cpp` 文件，但必须包含以下逻辑：

- Socket 初始化、连接、绑定、监听、接受和关闭。
- 菜单与连接状态管理。
- 客户端接收线程和消息队列。
- 服务端客户端登记表和并发访问保护。
- 四类请求处理和消息转发。
- TCP 完整报文收发。
- 断开、异常、线程退出和资源清理。

服务端至少需要保护：

- 客户端登记表的增删查改。
- 同一客户端 Socket 的并发发送，避免两条报文交错。

## 九、实验结果分析问题

需要结合实际运行结果回答：

1. 客户端是否需要调用 `bind()`？客户端源端口如何产生？多次调用 `connect()` 时端口是否保持不变？
2. 在服务端 `listen()` 和 `accept()` 之间设置断点时，客户端调用 `connect()` 是否能立即成功？
3. 服务端在同一个监听端口接收多个客户端数据时，如何区分数据属于哪个客户端？
4. 客户端主动断开后 TCP 连接处于什么状态？状态保持多久？使用 `netstat -an` 观察并记录。
5. 客户端断网后异常退出，服务端 TCP 状态如何变化？服务端如何检测连接是否仍然有效？
